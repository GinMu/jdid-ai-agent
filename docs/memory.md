## 1. 先把概念说清

| 概念 | 含义 | 在本项目里对应什么 |
| --- | --- | --- |
| 短期记忆 | 一次会话内的上下文:用户说了什么、调过哪些工具、结果是什么 | LangGraph 的 `AgentState.history` + `message` |
| 长期记忆 | 跨会话保留的知识/偏好 | 只有"知识库"(`knowledge/`,公共资料),**用户历史没有** |
| 上下文窗口 | 模型一次能接收的 token 上限 | 由模型决定;我们**没有**折算与限流 |
| 上下文预算 | 我们主动给历史留的额度(通常按字符近似 token) | **未设置**(M6) |
| 滑动窗口 | 只保留"最近一段"历史,超出部分丢弃 | **未实现**(M6) |
| 摘要压缩 | 把旧历史压成几句话再放回上下文 | **未实现**(M8) |
| 记忆检索 | 不把历史全塞进去,而是按需检索相关旧对话 | **未实现**(M9) |
| 遗忘策略 | TTL / LRU / 显式清除 | **未实现**(M7) |

> 有两个"窗口"容易混淆:`policy.RateLimiter` 里也有一个 60 秒的滑动窗口,那是**限流**,
> 和这里说的"上下文窗口"不是一回事。

## 2. 已实现的策略(M1–M5)

### M1 会话隔离

```text
/chat  →  body = {"session_id": <uuid>, "message": …, "turns": 0}
        →  LangGraph config = {"configurable": {"thread_id": session_id}}
```

`thread_id` 就是会话 id;App 侧用 **UUID v4**(`newAiSessionId()`),避免像 6 位随机数那样撞车。
撞了的后果不是"回答混了",而是两段对话共享同一份图状态(可能续上别人的挂起工具调用)。

### M2 会话内工具历史

每个工具结果都以**一条记录**追加进 `history`:

```json
{ "tool": "list_credentials", "args": { "limit": 50 }, "tool_call_id": "call_1",
  "result": { "total": 7, "items": [] } }
```

回放时(`planner._messages`)把它渲染成一条**用户消息**:

```text
[工具 list_credentials 的真实结果]
{"total": 7, "items": []}
(这是已经取到的数据:请直接基于它回答,不要再调用同一个工具。)
```

不用 `assistant(tool_calls)` + `tool` 消息对的原因写在 `docs/structured-output.md` 与提交 `ca9884d`:
OpenAI 兼容端点要求严格配对,DeepSeek thinking 模式还要求回传 `reasoning_content`,而
`langchain-deepseek` 只读不写 —— 第二次工具调用必 400。

`interrupt()` / `Command(resume=…)` 依赖 `MemorySaver` 保存状态,所以"挂起等钱包"这件事本身也是一种记忆。

### M3 单轮熔断

`max_turns=6`:同一条用户消息内,工具往返超过 6 次就停下并回一句"这轮已经查得够多了"。
注意 `turns` 在 `/chat` 里被重置为 0,**只约束当轮**,不约束会话总长度。

### M4 单次结果有界

| 参数 | 上界 | 位置 |
| --- | --- | --- |
| `list_credentials.limit` | 50 | 服务端 schema + 钱包侧夹取 |
| `list_nfts.limit` | 50 | 同上 |
| `query_knowledge.top_k` | 8 | 服务端 schema |
| 知识库单片段 | 700 字符 | `knowledge.MAX_SNIPPET` |

这是"让每次输入别太大",**不是**窗口 —— 会话久了总量仍会涨。

### M5 审计

`AuditLog(200)` 是内存环形缓冲,只记事件与工具名,**不记原文**(参数走 `redact()`)。

## 3. 滑动窗口:当前没有做(M6,`TODO`)

### 现状与风险

`history` 在会话内**只增不减**,`_messages()` 每次都把它全量回放。于是:

| 风险 | 说明 |
| --- | --- |
| 上下文膨胀 | 连续问 20 次凭证、每次 7 条摘要,历史会到几十 KB;再叠加知识库片段更容易顶到模型上限 |
| 成本与时延 | 与膨胀同步线性上涨 |
| 硬失败 | 超过模型上下文 → provider 4xx → `_explain()` 给出错误,但用户只看到"失败" |
| 内存泄漏 | `MemorySaver` 没有淘汰:会话越多,进程内存越大,且重启即丢 |

### `TODO` 设计:v1 滑动窗口

**预算单位**:字符(近似 token:中文约 1 字符 ≈ 1 token,英文约 4 字符 ≈ 1 token)。
配置项 `DID_AI_CONTEXT_BUDGET`(默认 24 000 字符)。

**剪切单位是"块",不是"条"**:一次工具调用的 `request + result` 视为一整块。
绝不在 JSON 中间截断 —— 半个 JSON 比没有更糟(模型会误读成"数据不完整")。

**顺序**(从最旧开始丢,直到进预算):

```text
system prompt                         ← 永不丢
[早期 N 次工具结果已省略]             ← 占位,让模型知道"有历史被丢"
最近 K 个工具块(整块保留)           ← 越新越优先
当前用户消息                          ← 永不丢
```

**保留"摘要头"而不是全部丢**:会话里维护一个 `memory_facts`(当前 DID、已确认过的结论),
它很小、不进窗口、每轮随 system prompt 一起给模型 —— 这样丢掉旧块也不会"失忆"到连身份都不知道。

**触发点**:`plan_node` 组装消息前调用纯函数 `trim_history(history, budget)`。

**可观测**:`context_trim session=… dropped=3 chars=38000→9100`,同时进 `/audit`。

**测试**(纯函数,必做):

| 用例 | 断言 |
| --- | --- |
| 未超预算 | 原样返回,顺序不变 |
| 超预算 | 从最旧开始丢,剩余总字符 ≤ 预算 |
| 整块性 | 不会出现"只有 result 没有 tool 名"的半块 |
| 单块超预算 | 只保留这一块 + 占位,不崩 |
| 占位 | 有丢弃时首条是 `[早期 … 已省略]` |

## 5. 决策表

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 丢"整块"还是按字符截断 | 整块 | 半个 JSON 会被模型当成有效数据,错误更难发现 |
| 先丢工具结果还是先丢用户消息 | 工具结果 | 用户的原始问题定义了任务,丢了等于换题 |
| 丢弃时留占位还是静默 | 留占位 | 让模型知道"信息不全",可以主动说"我再查一次" |
| 是否一开始就摘要压缩 | 否 | 多一次调用与延迟;窗口先解决 80% 问题 |
| 记忆是否需要长期化 | 知识库已长期,用户历史暂不做 | 钱包场景下"记住我上次问了什么"价值有限,且涉及隐私保留期 |

## 8. 业界成熟策略清单(选型用)

因为 M6(滑动窗口)、M8(摘要)、M9(长期记忆)都还没做,这里把**已经被验证过**的做法列全,
每条都给"核心机制 / 优点 / 局限 / 对本项目的适配度 / 落地成本",方便直接拍板。

| 编号 | 策略 | 代表实现 | 核心机制 | 优点 | 局限 | 本项目适配 | 成本 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| S1 | 固定窗口 | LangChain `trim_messages`、LlamaIndex `ChatMemoryBuffer` | 只保留最近 N 条消息或 N 个 token | 实现最简单、行为可预测 | 早期信息直接消失 | 高(兜底) | 小 |
| S2 | Token 感知窗口 + 不拆工具对 | `trim_messages(..., allow_partial=False)` | 按预算从旧到新删,**成对**保留 `tool_call`/`tool_result` | 不会产生半个 JSON;预算可控 | 仍会丢信息 | **最高** | 小 |
| S3 | 滚动摘要 | LangChain `ConversationSummaryBufferMemory` | 超出预算的旧消息压成一段摘要,替换原消息 | 比纯窗口"记得更多" | 摘要会失真;每轮多一次调用 | 高 | 中 |
| S4 | 分层/递归摘要 | map-reduce summarization | 分段摘要再归并 | 超长历史也能压进窗口 | 实现复杂、延迟高 | 中 | 大 |
| S5 | 显式记忆槽 | LangGraph `state` + reducer、scratchpad | 关键事实(当前 DID、结论)存成结构化字段,不进历史 | 极小、稳定、不依赖模型 | 需要人为定义字段 | **最高**(配 S2) | 小 |
| S6 | 情景记忆检索 | [mem0](https://github.com/mem0ai/mem0)、自建 RAG | 旧对话切片入库,新一轮按 query 召回 top-k | 上下文恒定;"记得多"由检索负责 | 需要向量/索引与召回质量 | 高(已有 BM25 可复用) | 中 |
| S7 | 时序知识图谱 | [Graphiti (Zep)](https://github.com/getzep/graphiti) | 把对话抽成实体+关系+有效期,按时间查询事实 | 能回答"上个月那个 DID 是谁" | 依赖抽取质量,工程重 | 低(钱包场景暂无时间推理需求) | 大 |
| S8 | 分层记忆系统 | [MemGPT / Letta](https://github.com/letta-ai/letta)([论文](https://arxiv.org/abs/2310.08560)) | core(常驻)/ recall(可搜)/ archival(冷存),模型自主分页 | 长任务表现最好 | 复杂、调用多、调试难 | 中(长期演进方向) | 大 |
| S9 | 事实抽取存储 | 自建 profile / KV | 只存"用户偏好、常用 DID"等结构化事实 | 极小、可解释、可审计 | 抽取规则要维护 | 中 | 小 |
| S10 | 持久化 + 淘汰 | LangGraph checkpointer(SQLite/Postgres/Redis) | 状态落外部存储 + TTL/LRU | 重启不丢、可多实例 | 引入外部依赖 | 高(生产必需) | 中 |
| S11 | 前缀/上下文缓存 | [DeepSeek 上下文缓存](https://api-docs.deepseek.com/guides/kv_cache) | 稳定前缀复用 KV,降低单价与首字延迟 | 不改行为、省钱 | 不解决窗口大小 | 高(零改动可受益) | 极小 |

### 反模式(明确不做)

| 反模式 | 为什么 |
| --- | --- |
| 按字符数**硬切**历史(切在 JSON 中间) | 半个 JSON 会被模型当成有效数据,错误更难发现 |

| 只靠加大窗口/换长上下文模型 | 成本线性上涨,且不解决"该记什么" |

## 9. 冲突与预算:上下文放不下时谁先被删

当"对话历史 + 长期记忆 + 用户新指令"三者打架,又超出上下文预算时,
需要一条**确定的裁决顺序**。下面是建议规则(窗口仍是 `TODO`,规则先定下来,实现时才有依据)。

### 9.1 优先级(高 → 低)

| 级别 | 内容 | 能否被删 |
| --- | --- | --- |
| P0 | 安全约束(不得索取私钥、写操作必须确认) | **永不** |
| P1 | 用户**当前这条**指令 | **永不** |
| P2 | 用户显式设定的长期约束("以后都用中文""不要签名") | 仅在其被新指令取代后 |
| P3 | 最近 K 个工具结果(当前任务的事实) | 预算不足时从最旧删 |
| P4 | 更早的工具结果 | 可删,留占位 |
| P5 | 更早的对话文本 | 可删,可摘要 |
| P6 | 推断型记忆(置信度低) | 优先删 |

两条容易搞反的:**P1 高于 P2**(当场说的赢过以前设的),而 **P0 高于一切**(用户要求也不能让它泄露私钥)。

### 9.2 删减顺序(从先删到后删)

```text
① 过期记忆(超过 expiresAt)          ← 先清,不占预算
② 与当前指令冲突的旧记忆             ← 冲突就必须出局,见 9.3
③ 低置信推断记忆
④ 最旧的工具结果(整块)              ← 留占位 [早期 N 次工具结果已省略]
⑤ 更早的对话文本(可先摘要再删)
⑥ 最近 K 个工具结果(仅保留最后一个)
最后才动:P2 记忆 → P1 → P0(理论上不该发生,触发即告警)
```

### 9.3 旧记忆与新指令冲突时:旧值必须"出局",而不是"留在上下文里"

这是最容易出错的地方:**如果只是"优先用新的",旧值仍留在上下文里,模型就有机会被它带偏。**
正确做法是**在注入上下文之前就把它标记为失效**:

| 冲突 | 处理 |
| --- | --- |
| 新指令与某条记忆互斥 | 该记忆标记 `supersededAt` + `supersededBy`,**不进本轮上下文** |
| 新指令与历史对话里的旧结论互斥 | 旧结论保留为史实,但在上下文里降级为"此前提到过" |
| 记忆与本次工具实测冲突 | **以工具结果为准**(实测 > 缓存),并回写记忆 |
| 无法判断是否冲突 | 保守:不进上下文,只在资料区放一句"可能有旧设置,已被本次要求覆盖" |

### 9.4 写入时的顺序声明

上下文里的顺序本身会传递"权重",建议固定为:

```text
[system] 角色 + 安全约束
[user]   用户当前这条指令            ← 最靠近末尾,权重最高
[data]   工具结果与记忆(明确标注"以下是参考数据")
```

记忆放在**数据区**而不是 system 区,结构上就降低了"旧记忆压过新要求"的概率 ——
这是低成本、纯提示层的手段,配合 9.3 的失效标记才完整。

## 10. 冲突的测试用例(实现窗口时必须有)

| 用例 | 输入 | 断言 |
| --- | --- | --- |
| 新指令覆盖旧记忆 | 记忆"用英文" → 用户说"以后用中文" | 回答用中文;旧记忆被标记 superseded |
| 冲突记忆不进上下文 | 记忆"默认身份 A" → 用户说"这次查 B" | 本轮上下文不含"默认身份 A" |
| 过期记忆不引用 | 记忆"凭证已验证"(已过期) | 回答不声称已验过,重新验证 |
| 实测优于缓存 | 记忆"7 张凭证" → 工具返回 3 张 | 用 3 张,并把记忆更新为 3 |
| 显式撤销 | 用户说"忘掉我的默认身份" | 该记忆删除,不再出现在后续上下文 |
| 推断不得覆盖显式 | 推断"喜欢简洁" + 显式"要详细" | 用详细 |

相关设计见 [`docs/long-term-memory.md`](long-term-memory.md) 第 11–12 节(记忆更新与裁决)与
[`docs/summarization.md`](summarization.md)(超预算时的压缩)。

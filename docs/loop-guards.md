# 死循环:有哪些限制,以及怎么定位

这份文档把 did-ai-agent 里与"无限循环"有关的护栏、缺口和排查手法写在一起,
方便线上出现"一直转圈/一直调同一个工具/一直计费"时按图索骥。

> 结论先行:**唯一的图内环是 `request_tool → plan`,靠 `max_turns=6` 熔断**;
> 图外还有提示词、限流、参数上界、客户端互斥四层。
> 但 `/resume` 目前**无限流也不校验 pending**,是最大的缺口(见 G1)。

## 1. 死循环的五种形态

| 形态 | 表现 | 本项目风险 |
| --- | --- | --- |
| 模型绕圈 | 反复调用同一个工具、参数几乎不变 | **有**(读工具幂等,最容易发生) |
| 图结构成环 | 节点 A→B→A 无终止条件 | 环存在,但有熔断 |
| 客户端重放 | 重复点"继续/确认"、重复提交同一结果 | 有 `busy` 互斥,基本挡住 |
| 重试风暴 | 失败后立刻重试、没有退避 | 目前没有自动重试,风险低但也没有退避 |
| 用户连点 | 快速发多条消息 | 限流 30/min + `busy` |

## 2. 现有护栏(五层)

| 层 | 机制 | 参数 | 触发后 | 代码位置 |
| --- | --- | --- | --- | --- |
| 提示词 | 规则 6:已拿到结果就直接用,不要重复调同一工具 | — | 模型自行收敛 | `planner._SYSTEM_PROMPT` |
| 图 | `max_turns` 熔断:工具往返次数到上限就收尾 | 6 | 返回"这轮已经查得够多了…" | `graph.plan_node` |
| 图 | 唯一环 `request_tool → plan`;`route()` 在 error/pending 为空时收敛到 `finish` | — | 结束本轮 | `graph.build_graph` |
| 接口 | 每会话限流(60 秒滑动窗口) | 30 次/分钟 | 抛 `PolicyError`(请求被拒) | `policy.RateLimiter`、`app.chat` |
| 参数 | 单次结果上界:`limit≤50`、`top_k≤8`、知识片段 700 字符 | — | 夹取/截断,避免一次拉爆 | `tools/registry.py`、`knowledge.py` |
| 客户端 | `busy` 互斥:发送/继续/确认都先判 busy | — | 重复点击直接 return | `AiAssistantViewModel` |

补充两个"看起来像、其实不是":

- **`turns` 在 `/chat` 里重置为 0**:`max_turns` 只约束**当轮**(一条用户消息内的工具往返),
  不约束整个会话;
- **`request_id = session:tool:turns`**:同一个 `turns` 值对应同一次往返,重复出现说明消息被重放。

## 3. 为什么还不够(缺口)

| 编号 | 缺口 | 后果 | 优先级 |
| --- | --- | --- | --- |
| G1 | **`/resume` 没有限流,也不校验是否存在 pending** | 客户端异常时可被反复调用;没有挂起时还会**直接开新一轮**(实测过) | P0 |
| G2 | 没有"同一工具 + 同一参数重复"的检测 | 模型换个说法继续调同一个工具,只能等熔断烧满 6 次 | P0 |
| G3 | 没有跨轮总预算 | 用户连续问 10 轮,每轮 6 次往返 = 60 次工具调用,只有限流兜底 | P1 |
| G4 | 模型调用没有显式超时与退避 | provider 卡住时请求悬挂(客户端 `busy` 一直为真) | P1 |
| G5 | 循环没有显式事件/指标 | 只能靠日志文本判断,做不了告警 | P2 |
| G6 | 客户端 `busy` 没有超时取消 | 网络半死时界面永久"正在思考…" | P2 |

## 4. 怎么定位死循环(操作手册)

### 4.1 先看症状对号

| 用户看到 | 先查什么 | 大概结论 |
| --- | --- | --- |
| 提案卡片反复出现同一个工具 | 同一 session 的 `tool_request` 是否同参数 | 模型绕圈(G2) |
| 最后一句是"这轮已经查得够多了…" | 该轮 `turns` 是否到 6 | 熔断生效,正常收尾 |
| 请求被拒/提示过于频繁 | 该 session 60 秒内次数 | 限流 |
| 界面一直"正在思考…" | 服务端是否收到 `/chat`,有没有 `done` | G1/G4/G6 |
| 同一条回答出现两次 | 客户端是否重复发 `/resume` | 客户端重放 |

### 4.2 服务端:按 session 切片

```sh
# 最近 200 行里,每个 session 各自调了哪些工具、多少次
grep tool_request logs/did-ai-agent.log | tail -200 \
  | sed -E 's/.*session=([^ ]+) tool=([^ ]+).*/\1 \2/' | sort | uniq -c | sort -rn | head

# 是否有反复出现的同一工具 + 同一参数(模型绕圈的典型指纹)
grep tool_request logs/did-ai-agent.log | sed -E 's/.*session=([^ ]+) tool=([^ ]+).*args=(.*)/\1 \2 \3/' \
  | sort | uniq -c | awk '$1>1' | head

# 熔断是否触发过
grep -c "这轮已经查得够多了" logs/did-ai-agent.log
```

`/audit` 里也能看到事件序列(只记工具名与 `kind`,不含原文):

```sh
curl -s localhost:8099/audit | python3 -m json.tool | less
```

### 4.3 关键字段怎么读

| 字段 | 含义 | 读法 |
| --- | --- | --- |
| `session` | 会话 id(UUID) | 一个用户对话一个值;多条交织说明并发或重放 |
| `tool` + `args` | 本次请求 | 与上一次完全相同 → 绕圈 |
| `request_id` 尾部数字 | 该轮的 `turns` | 递增说明还在同一轮里继续往返;归 0 是新的一轮 |
| `tool_result` 的内容 | 钱包回了什么 | 与上一次相同却还在调 → 模型没用上结果 |
| `resume` 行 | 客户端回了什么 | 与上一次相同 → 客户端重放 |

### 4.4 判定树

```text
同一 session 里 tool+args 重复出现?
├─ 是 → 模型绕圈:看 tool_result 是否为空/报错(模型可能没读懂)
│        ├─ result 有数据 → 提示词失效,考虑 G2 去重
│        └─ result 是 {"error": …} → 模型在重试同一个失败调用 → 应回传更明确的错误
└─ 否 → 熔断/限流?
        ├─ turns=6 → 熔断正常
        ├─ 429/提示频繁 → 限流正常
        └─ 都没有 → 看是否 /resume 被反复调用(G1),或客户端 busy 未复位(G6)
```

## 5. 建议加固

| 优先级 | 措施 | 实现要点 |
| --- | --- | --- |
| P0 | `/resume` 限流 + pending 校验 | 没有挂起时返回 409(`no pending`),不再"开新一轮";同时复用 `RateLimiter` |
| P0 | 重复调用拦截 | 本轮内维护 `(tool, canonical(args))` 集合,重复直接回 `{"error":"重复调用已被拦截"}`,并记 `loop_guard` 事件 |
| P1 | 往返次数进日志/审计 | `tool_request` 行补 `turns=N`,可直接 grep `turns=5` |
| P1 | 模型调用超时 | 给 `ChatDeepSeek` 设 `timeout`,并在图里加"单轮总时长"上限 |
| P2 | 循环指标 | `/metrics` 或 `/audit` 增加 `duplicate_calls`、`guard_hits`、`avg_turns` |
| P2 | 客户端超时取消 | `busy` 加超时(如 90s)复位,并提示"可重试" |

## 9. 设计问答:子任务失败与无人值守验收

### 9.1 失败分类决定处理方式

| 失败类型 | 例子 | 处理 | 为什么 |
| --- | --- | --- | --- |
| 瞬时 | 网络超时、链上节点忙 | **重试 1 次 + 退避** | 重试有效且安全(读操作幂等) |
| 参数/语义 | 凭证 id 不存在、DID 格式错 | **不重试**,回 `{"error":…}` 让模型改 | 重试不会变对 |
| 权限 | 用户拒绝确认 | **不重试**,结束 | 重试等于骚扰用户 |
| 部分成功 | 7 张凭证验了 3 张 | 返回"3 成功 + 4 未完成",让模型继续 | 全部失败会丢掉已完成工作 |
| 环境 | 服务未启动、模型 4xx | 降级话术 + 可重试提示 | 用户需要知道"能再试" |

### 9.2 降级策略(按顺序)

```text
工具失败
  → 换等价工具?(如本地文档 vs 链上解析)     ← 已实现:documentOf 网络优先/本地兜底
  → 用缓存结果?(带时间戳,并声明"可能过期")   ← TODO
  → 缩小范围?(只答已知部分)                  ← 已实现:凭证 0 条时说"读不到"
  → 明确告知失败 + 给出下一步                  ← 已实现:error 事件
```

### 9.3 无人值守时怎么验证"真的完成"

| 手段 | 说明 | 现状 |
| --- | --- | --- |
| **可验证结果** | 写操作后回读状态,而不是信"已提交" | 未做(写操作目前只到"提案") |
| 幂等键 + 去重 | 同一任务重复触发不产生第二次副作用 | 未做(G1/G2) |
| 心跳/租约 | 长任务定期续约,失联可接管 | 未做(单机单会话) |
| 独立校验通道 | 用另一个只读工具交叉验证(如"查凭证数"验证"签发成功") | 部分(可用现有工具组合) |
| 审计对账 | 定期核对审计日志与链上状态 | 未做 |

**原则**:**"执行成功"与"任务完成"是两件事** —— 前者是调用没报错,后者是目标状态确实达成。
无人值守必须以后者为准,所以每个写操作都要有"回读校验"。

**本项目现状**:写操作只生成提案,真正执行在钱包且需用户确认,因此"无人值守"范围很小;
上述手段在接入自动化写链前必须补齐(否则会出现"报告成功但链上没变")。

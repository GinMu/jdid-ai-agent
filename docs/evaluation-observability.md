# 评测与可观测性:流程设计、业界方案与落地清单

评测回答"效果好不好",可观测回答"为什么好/为什么坏"。两者必须一起设计:
**没有 trace 的评测无法归因,没有评测的指标无法判断好坏。**

> 现状先行:本项目有 46 个单元测试与四行结构化日志,**没有**评测集、没有 token 计量、
> 没有指标端点、没有 trace。本文给出目标流程、业界方案对比,以及按投入产出排序的落地清单。

## 1. 四层体系

| 层 | 做什么 | 频率 | 本项目现状 |
| --- | --- | --- | --- |
| L1 单元/契约 | 状态机、策略校验、解析器 | 每次提交 | **已有**(46 个测试) |
| L2 离线评测 | 固定任务集,断言轨迹与事实 | 每次 PR / 每日 | 无 |
| L3 在线可观测 | 日志、指标、trace | 持续 | 部分(日志) |
| L4 线上实验 | 灰度、A/B、抽样人工审 | 按需 | 无 |

L1 保证"代码没坏",L2 保证"任务能做对",L3 保证"线上看得见",L4 保证"改动可比较"。缺任何一层,
另外几层的结论都会失真。

## 2. 评测集怎么设计

### 2.1 用例结构

一条用例只描述"期望",不描述"实现":

```json
{
  "id": "credits-did-scope",
  "input": "帮我看看 did:swtc:jpAFbR1tzNMnmy4wfAycYtV33Jd288xYWx 有哪些凭证",
  "expect": {
    "must_call": ["list_credentials"],
    "must_not_call": ["propose_sign_message", "propose_issue_credential"],
    "args_include": { "list_credentials": { "did": "did:swtc:jpAFbR1tzNMnmy4wfAycYtV33Jd288xYWx" } },
    "facts": ["该 DID", "凭证"],
    "forbidden": ["私钥", "助记词", "我已完成签名"]
  }
}
```

### 2.2 断言分三层,优先级从高到低

| 层 | 断言什么 | 为什么优先 |
| --- | --- | --- |
| **轨迹** | 调了哪些工具、参数是什么、何时终止 | 稳定、可归因,不随模型措辞变化 |
| **事实** | 回答里是否出现关键事实(数量、id、verified) | 与用户价值直接相关 |
| 文本相似 | 与参考答案的相似度 | **尽量不用**:措辞差异会被误判成失败 |

### 2.3 指标(端到端 + 分解)

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 任务通过率 | 全部断言通过的用例占比 | 按版本追踪,不设绝对目标 |
| 工具选择正确率 | `must_call` 命中且未误调 | > 95% |
| 参数正确率 | `args_include` 全部满足 | > 95% |
| 观测利用率 | 回答引用了工具返回的事实 | > 90% |
| 终止正确率 | 该停就停、不空转 | > 95% |
| 幻觉率 | `forbidden` 命中或事实缺失 | < 2% |
| P95 延迟 / 每任务 token | 见 `docs/harness-matters.md` | 按基线 |

### 2.4 统计与防作弊

| 事项 | 做法 |
| --- | --- |
| 样本量 | 每类 ≥30,关键类别 ≥100 |
| 置信区间 | 用 Wilson 区间报告,不只报点估计 |
| 版本冻结 | 记录 `model`、prompt 哈希、工具 schema 哈希 |
| 防泄漏 | 评测用例不进提示词/示例;改动用例要评审 |
| 基线 | 每个版本与上一版比,而不是与"理想值"比 |

## 3. 可观测性怎么设计

### 3.1 三类信号

| 信号 | 内容 | 用途 |
| --- | --- | --- |
| 日志(events) | 一次请求的关键节点:chat / tool_request / resume / tool_result / error | 复盘单次会话 |
| 指标(metrics) | 计数与直方图:调用数、错误率、延迟、token | 看趋势与告警 |
| 追踪(traces) | 一次请求内的 span:plan → llm → validate → tool → resume | 定位耗时与失败点 |

### 3.2 关键字段(所有信号共用维度)

| 字段 | 说明 | 现状 |
| --- | --- | --- |
| `session_id` | 会话(thread_id) | 有 |
| `request_id` | `session:tool:turn` | 有 |
| `turn` | 本轮第几次工具往返 | **仅存在于 request_id,未独立记录** |
| `tool` / `kind` | 工具名与读/写 | 有 |
| `latency_ms` | 各阶段耗时 | **无** |
| `tokens_in` / `tokens_out` | token 计量 | **无** |
| `error_code` | 结构化错误码 | **无**(只有文本) |
| `guard_hit` | 熔断/重复调用/注入命中 | **无** |

### 3.3 隐私底线

| 规则 | 说明 |
| --- | --- |
| 不记原文 | 参数走 `redact()`,结果只记摘要 |
| 不记秘密 | 私钥/助记词/凭证原文永不落日志 |
| 结果截断 | 日志里的结果截断到可读长度(排查用) |
| 保留期 | 日志按天轮转,保留 N 天 |

### 3.4 采样与告警

| 对象 | 策略 |
| --- | --- |
| 失败请求 | **100% 保留**(最有价值) |
| 成功请求日志 | 全量(量小)或按会话采样 |
| trace | 按比例采样(如 10%),错误全采 |
| 告警 | 错误率、熔断率、限流率、P95 延迟、每会话 token |

## 4. 业界成熟方案

### 4.1 追踪与实验平台

| 方案 | 优点 | 缺点 | 适配 |
| --- | --- | --- | --- |
| **Langfuse**(开源/云) | 自托管、OTel 友好、prompt 版本与数据集 | 需要运维;生态较新 | **高**(先本地跑) |
| LangSmith | 与 LangChain/LangGraph 深度集成,开箱即用 | 托管(数据出域)、按量付费 | 中(敏感数据不适合) |
| Arize Phoenix | 开源、OTel、内置 eval | 功能面偏研究,运维成本 | 中 |
| Braintrust / Humanloop | 评测与实验体验好 | 商业、成本高 | 低 |
| Helicone / Portkey | 网关式埋点,接入极快 | 只看到请求层,缺业务轨迹 | 中 |
| W&B Weave | 与训练体系一体化 | 偏 ML 团队 | 低 |

### 4.2 指标与追踪基础设施

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| **OpenTelemetry + Prometheus + Grafana** | 事实标准、厂商中立 | 组件多,需自建 |
| Jaeger / Tempo | 追踪专用,成熟 | 仍要配采集 |
| 云厂商 APM | 接入快 | 锁定、成本 |

### 4.3 评测工具

| 方案 | 优点 | 缺点 | 适配 |
| --- | --- | --- | --- |
| **自建 pytest 评测集** | 零依赖、可进 CI、断言自由 | 无 UI、需自己写报告 | **高**(起步最优) |
| DeepEval | 断言丰富(pytest 风格) | 依赖较重,指标偏通用 | 中 |
| Ragas | RAG 指标专业(忠实度/召回) | 只覆盖 RAG 部分 | 中 |
| promptfoo | CI 友好、对比多模型 | 偏 prompt 对比 | 中 |
| AgentDojo / InjecAgent / BIPIA | 安全基准,业界可比 | 场景与钱包不同,需裁剪 | 中(安全专项) |
| garak | 红队扫描 | 不是常规回归 | 中 |
| Evidently | 数据/行为漂移 | 偏 ML 监控 | 低 |

### 4.4 LLM-as-judge 的用法与风险

| 事项 | 建议 |
| --- | --- |
| 用在哪 | 主观质量(是否答非所问、解释是否清楚) |
| 不要用在哪 | 可验证事实(数量、id、verified)——用断言更可靠 |
| 校准 | 用 30–50 条人工标注对齐,报告 judge 与人的一致率 |
| 风险 | judge 有位置/长度偏好,且会随模型升级漂移 |

| 名称 | 类型 | 标签 | 说明 |
| --- | --- | --- | --- |
| `agent_chat_total` | counter | `status` | 每轮用户消息 |
| `agent_tool_call_total` | counter | `tool`, `kind`, `status` | 工具调用 |
| `agent_tool_latency_ms` | histogram | `tool` | 工具耗时 |

## 7. 闭环流程

```text
用例集 → CI 跑评测 → 报告(轨迹+事实+延迟)
   ↑                        │
   │                        ├─ 失败 → 归因(规划/工具/参数/推理) → 修复 → 加用例
   │                        └─ 通过 → 发布
线上 → 日志/指标/trace → 抽样人工审 → Bad Case → 回填用例集
```

关键:**线上发现的问题必须回到用例集**,否则同一个坑会踩第二次。

## 8. 反模式

| 反模式 | 为什么有害 |
| --- | --- |
| 只跑端到端,不看轨迹 | 失败无法归因,只能猜 |
| 用文本相似度做主判据 | 措辞差异被误判,改一个字就"失败" |
| 没有基线就报百分比 | 无法判断改动好坏 |
| 指标没有维度 | 知道"错误率 5%",不知道错在哪 |
| 日志记原文 | 隐私风险,且噪音大 |
| 评测集当提示词示例用 | 数据泄漏,分数虚高 |
| 只做评测不做观测 | 线上问题看不见 |
| 只做观测不做评测 | 看得见但判断不了对错 |

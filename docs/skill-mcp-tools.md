# Skill、MCP、TOOLS:三者分别解决哪一层问题

这三个词经常被混用,但它们解决的是**不同层**的问题。混用会导致选错工具:
把"流程知识"写成工具、把"一个工具"包装成 MCP server、或者把"连接协议"当成能力。

> 一句话:**TOOLS 是手脚(能做什么),MCP 是插头(能力从哪来、怎么复用),Skill 是操作规程(这类任务该怎么做对)。**

## 1. 三者各是什么

| 概念 | 一句话定义 | 形态 | 谁定义 |
| --- | --- | --- | --- |
| **TOOL** | 模型可以调用的**单个动作**,有名字、参数 schema、执行者 | 函数/接口(JSON schema) | 应用开发者 |
| **MCP** | 把工具/资源/提示按**标准协议**暴露给任意 client 的**连接层** | JSON-RPC 服务(tools / resources / prompts) | 服务提供方,跨应用复用 |
| **Skill** | 一类任务的**程序性知识与流程**,按需加载到上下文 | 说明文档(+可选脚本/资源) | 领域专家/团队 |

### 1.1 TOOL:能力的最小单位

```json
{
  "name": "list_credentials",
  "description": "列出凭证摘要(类型、发行方、是否过期)",
  "parameters": { "type": "object", "properties": { "did": {"type": "string"} } }
}
```

工具回答的是:**“我能做哪一件具体的事,参数是什么,返回什么。”**
它不解释“什么时候该做”“分几步做”“做完怎么验收”。

### 1.2 MCP:能力的运输与复用层

MCP(Model Context Protocol)规定 client 与 server 之间的发现与调用方式,
server 通常暴露三类东西:

| 原语 | 作用 | 例子 |
| --- | --- | --- |
| `tools` | 可调用的动作 | `did_resolve`、`did_stat` |
| `resources` | 可读取的数据 | DID 文档、审计记录 |
| `prompts` | 预置的提示模板 | “解释一张凭证” |

它回答的是:**“这些能力怎么被不同的应用/语言/客户端以统一方式接入。”**
参考:[MCP 规范](https://modelcontextprotocol.io/specification/2025-11-25/server/index.md)。

### 1.3 Skill:任务级的流程知识

Skill 通常是一份 `SKILL.md` 之类的说明:适用场景、步骤、检查项、常见坑、何时该用哪个工具,
必要时附带脚本或模板。它回答的是:**“这类任务怎么做对、别漏哪几步。”**

典型内容:

```text
何时使用:用户要给钱包加一个 dApp 页面
步骤:1) 读契约 2) 生成页面 3) 跑 conformance 4) 真机验证
检查:必须声明用到的钱包能力;错误码要覆盖 400/401 分支
```

参考:[Anthropic: Equipping agents with Agent Skills](https://www.anthropic.com/research/equipping-agents-for-the-real-world-with-agent-skills)、
[Agent Skills 文档](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview)。

## 2. 各自解决哪一层

| 层 | 问题 | 由谁解决 |
| --- | --- | --- |
| 能力层 | “能不能做成这件事” | **TOOL** |
| 集成层 | “能力怎么跨应用/跨语言复用、怎么发现” | **MCP** |
| 流程层 | “这类任务该按什么步骤做、有哪些约束” | **Skill** |
| 上下文层 | “模型这一轮看到什么” | prompt / 记忆 / RAG(见 `docs/memory.md`) |
| 安全层 | “谁允许它做、出事了怎么拦” | 白名单 + 确认 + 注入防护(见 `docs/prompt-injection.md`) |

三者的关系可以画成这样:

```text
Skill(怎么做对)
  └─ 引用 TOOL(做什么)
        └─ TOOL 可以由本地实现,也可以由 MCP server 提供(能力从哪来)
```

举例:一个 “did-method-qa” skill 会写清“先检索知识库、再引用来源、不要编造”;
它用到的 `query_knowledge` 是本项目的本地工具;而 `did_resolve` 这类能力未来可以由
钱包侧的 MCP server 提供。

## 3. 对比表(选型时看这张)

| 维度 | TOOL | MCP | Skill |
| --- | --- | --- | --- |
| 粒度 | 单个动作 | 一组能力的服务 | 一类任务 |
| 生命周期 | 随应用发布 | 独立进程/服务,可跨应用 | 随知识库更新 |
| 谁执行 | 应用(或钱包设备) | MCP server | 无执行,只提供知识与流程 |
| 模型怎么看到 | function schema | 发现后转成 schema | 按需加载的文本 |
| 变化频率 | 低(schema 稳定) | 中(服务升级) | 高(流程/文档常改) |
| 失败模式 | 参数错、越权、选错工具 | 服务不可用、权限范围、工具描述注入 | 上下文膨胀、内容过期、与提示词冲突 |
| 主要风险 | 能力过宽 | **供应链信任** | **知识漂移** |

## 4. 常见误区

| 误区 | 为什么错 |
| --- | --- |
| 把流程写进工具描述 | 工具描述是“单动作说明”,塞流程会让模型抓不住重点,且改流程就要改接口 |
| 为一个工具写一个 MCP server | MCP 的价值是**复用与发现**;只有一个工具时直接函数调用更简单 |
| 把 Skill 当工具用 | Skill 没有执行能力,它只是“告诉模型怎么做” |
| 用 MCP 解决权限问题 | MCP 是传输层,权限仍要靠白名单/OAuth/确认 |
| 三者混在一层评估 | 评估指标不同:工具看参数正确率,Skill 看流程完成率,MCP 看可用性与延迟 |

## 5. 本项目的现状

| 项 | 状态 | 说明 |
| --- | --- | --- |
| TOOL | **已实现** | `tools/registry.py` 共 11 个:钱包只读 7 + 写提案 3 + 本地知识库 1 |
| MCP | **未接入** | 生态里已有钱包 MCP server(`JCCDex/jdid-dapp-sdk` 的 `mcp/`),但它服务的是 dApp 调试,不在本服务的调用链上 |
| Skill | **未实现** | 本仓没有 skill 机制;`docs/` 只是人类文档,不会自动进模型上下文 |

也就是说:现在模型的能力来自**工具白名单**,流程约束来自**系统提示词**,
知识来自**本地 RAG**;没有"按需加载 SOP"和"标准协议接入"这两层。

## 6. 如果要在这三个方向推进

| 方向 | 建议 | 收益 | 成本 |
| --- | --- | --- | --- |
| Skill | 建 `skills/` 目录,每个 skill 一份说明 + 触发条件;按“问题类型”注入 | 复杂任务步骤稳定、少靠提示词碰运气 | 低 |
| MCP(消费) | 让服务端能连**本地** MCP server(钱包侧),把 `did:*` 能力标准化 | 能力与实现解耦;跨客户端复用 | 中 |
| MCP(提供) | 把本服务的 `query_knowledge` 以 MCP 暴露 | 其他客户端也能问 did 方法 | 低 |
| TOOL | 继续按需加,但保持白名单与 schema 纪律 | — | 低 |

建议顺序:**先 Skill(最便宜、收益直接)→ 再 MCP 消费 → 最后 MCP 提供**。

### 6.1 Skill 落地要点

| 要点 | 说明 |
| --- | --- |
| 触发条件写清楚 | “用户问 did:swtc 方法时用本 skill”,否则模型不知道何时加载 |
| 体积受控 | 单个 skill ≤ 2 KB,避免把上下文吃满 |
| 只写流程,不写事实 | 事实放 RAG,skill 放步骤,避免两处维护 |
| 有检查项 | 例如“回答必须给出来源”“不得声称已执行写操作” |

### 6.2 MCP 接入要点

| 要点 | 说明 |
| --- | --- |
| 信任来源 | 只连本地/受信 server;记录版本与哈希 |
| 权限范围 | 能用只读就别给写;写操作仍走确认 |
| 工具描述视为不可信 | 恶意 server 可把注入写进工具描述(见 `docs/prompt-injection.md`) |
| 命名冲突 | 多个 server 的工具名要加前缀 |
| 失败降级 | server 挂了要能回落到本地工具 |

## 9. 设计问答:内部接口如何封装成 MCP

把现有 `query_knowledge` 这类内部能力包成 MCP server 时,要回答四个问题:

### 9.1 Schema:直接复用现有工具 schema

| 项 | 做法 | 理由 |
| --- | --- | --- |
| 命名 | `did_query_knowledge`,带领域前缀 | 多 server 并存时避免冲突 |
| 参数 | 沿用 `tools/registry.py` 的 JSON Schema | 一处定义、两处生效(FC 与 MCP 共用) |
| 输出 | 结构 + 文本双份:`content:[{type:"text"}]` + `structuredContent` | 老客户端读文本,新客户端读结构 |
| 版本 | server 暴露 `version`,schema 变更走大版本 | 客户端可判断兼容性 |

### 9.2 错误信息:区分"协议错"与"业务错"

| 类型 | 例子 | 表达方式 |
| --- | --- | --- |
| 协议错 | 参数不合法、未知工具 | JSON-RPC error(-32602 等),**不要**塞进 content |
| 业务错 | 检索无结果、上游超时 | `isError: true` + 可读文本,让模型能自纠 |

理由:协议错是"调用方写错了",业务错是"这次没办成";混在一起会让模型把协议错当业务错去改参数。

### 9.3 流式返回

| 场景 | MCP 机制 | 本项目现状 |
| --- | --- | --- |
| 长时间任务 | progress notification(`notifications/progress`) | 未用;检索是毫秒级 |
| 增量结果 | server 主动发消息 | 未用 |
| 与 SSE 的关系 | MCP 可用 stdio 或 Streamable HTTP | 本服务已有 SSE,仅面向 App,不是 MCP |

结论:**当前检索类工具不需要流式**;要流式的场景(大文档解析)应先做分页/进度,再谈流。

### 9.4 兼容性

| 变更 | 能否兼容 | 做法 |
| --- | --- | --- |
| 新增可选参数 | 兼容 | 默认值 + 旧客户端不变 |
| 新增返回字段 | 兼容 | 客户端忽略未知字段 |
| 改字段语义 | **不兼容** | 升大版本 + 双写一段时间 |
| 删参数 | 不兼容 | 先标记 deprecated,再删 |

- [ ] 协议错/业务错分开

## 10. 设计问答:Skill、MCP、FC、CLI、Runtime 的区别

| 概念 | 是什么 | 谁执行 | 模型怎么感知 | 典型用途 |
| --- | --- | --- | --- | --- |
| **Function Calling** | 模型输出结构化调用,应用执行 | 应用 | 工具 schema 列表 | 单动作调用 |
| **MCP** | 标准化暴露工具的协议 | MCP server | 发现后转成 schema | 跨应用复用 |
| **Skill** | 任务级流程知识(说明 + 可选脚本) | 无(人或 agent 按其执行) | 按需加载的文本 | 复杂任务 SOP |
| **CLI** | 命令行程序 | 操作系统 | 通过 shell 工具间接用 | 运维、构建、批处理 |
| **Runtime** | 承载 agent 与工具的运行时(容器/沙箱/调度) | 平台 | 不感知 | 隔离、扩缩容、生命周期 |

一句话区分:**FC 是"怎么调"、MCP 是"从哪调"、Skill 是"该怎么做"、CLI 是"用命令做"、Runtime 是"在哪跑"。**

### 10.1 Skill 如何按需加载

| 方案 | 机制 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 全量注入 | 所有 skill 塞进 system prompt | 实现最简单 | 上下文膨胀,互相干扰 |
| **触发词匹配**(推荐起步) | 命中关键词才注入 | 便宜、可预测 | 漏触发 |
| 检索式加载 | 用 `knowledge.py` 的 BM25 检索 skill 描述 | 可扩展、免手工维护 | 需要 skill 描述写好 |
| 模型自选 | 先给"skill 清单",模型要用哪个再读全文 | 最灵活 | 多一次往返,可能漏 |

推荐:**触发词 + 检索兜底**。skill 描述里必须写清"何时使用",否则以上三种都会失效。

## 11. 设计问答:工具很多时如何稳定选对

### 11.1 为什么会选错

| 原因 | 表现 |
| --- | --- |
| 工具太多 | 相似工具混用(如 `get_credential` 与 `list_credentials`) |
| 描述含糊 | 参数漏填、用错场景 |
| 命名不规范 | 前缀缺失,模型靠猜 |
| 返回相似 | 选对了也用不对 |

### 11.2 描述优化清单

- [ ] 一句话说清"做什么",再说"什么时候用"
- [ ] 参数逐个写 `description`,枚举值列全
- [ ] 说明**不做什么**(如"不含凭证原文")
- [ ] 相似工具给出区分句("要单张用 get_credential,要列表用 list_credentials")
- [ ] 可选参数写清默认行为

### 11.3 工具检索与动态加载

| 方案 | 机制 | 适用规模 | 成本 |
| --- | --- | --- | --- |
| 全量暴露 | 所有工具一次给模型 | <20 | 无 |
| **分组加载** | 按领域分组,先给组再给组内工具 | 20–100 | 低 |
| **工具检索** | 用 BM25/向量检索工具描述,只给 top-k | 100+ | 中(可复用 `knowledge.py`) |
| 层级路由 | 先选领域 agent,再选工具 | 1000+ | 高 |

**本项目现状**:11 个工具,全量暴露即可;但**工具描述已经是最重要的质量杠杆** ——
`did` 可选参数写清后,模型才开始正确传参(见 `docs/harness-matters.md` 第 4 节)。

# 历史对话的摘要压缩

这份文档回答:为什么要把历史压成摘要、现在 did-ai-agent 有没有做、成熟解法有哪些、
以及如果要做,具体怎么设计(含提示词与失败降级)。

> 结论先行:**当前没有做**。历史 `history` 在会话内只增不减,既没有窗口也没有摘要
> (`docs/memory.md` 里的 M6/M8)。本文的"成熟解法"与"推荐设计"是选型材料,不是现状。

## 1. 为什么要做摘要压缩

会话变长时,把全部历史塞回模型有四个代价,摘要压缩就是拿"一部分细节"换这四项:

| 问题 | 不加摘要会怎样 | 摘要能换回什么 |
| --- | --- | --- |
| 上下文预算 | 历史线性增长,迟早顶到模型窗口;顶到就是 provider 4xx,用户只看到"失败" | 把 30 轮压成 5 行,预算回到常量级 |
| 成本 | 每次请求都重发全部历史,input token 与账单线性上涨 | input 体积下降一个数量级 |
| 时延 | 首字延迟随 input 变长而变长(即使有缓存也不为零) | 首字更快,交互更像"流式" |
| 任务连续性 | 硬截断会丢"用户到底要什么",模型开始答非所问 | 摘要保住**意图、结论、已排除项**,细节可再查 |

反过来说,**不是所有信息都值得压**:ID、数字、过期时间这类"压缩后容易失真"的内容,
应该以**结构化事实**(memory_facts)保存,而不是交给自然语言摘要去概括。

## 2. 当前项目做了什么

| 事项 | 状态 | 证据 |
| --- | --- | --- |
| 会话内历史 | 全量保留 | `AgentState.history`,`_messages()` 全量回放 |
| 滑动窗口 | 未做 | `docs/memory.md` M6 |
| **摘要压缩** | **未做** | 代码里没有摘要节点/摘要调用;`FakePlanner._summarize` 只是离线测试用的"把最近一条结果拼成人话",不是压缩 |
| 结构化事实槽 | 未做 | M5 之外的 `memory_facts` 只在设计里 |
| 结果侧裁剪 | 已做 | 工具只回摘要、`limit≤50`、知识片段 700 字符 —— 这是"少进",不等于"压缩历史" |

也就是说:现在能控制的是**单次结果大小**,控制不了**历史长度**。

## 3. 成熟解法

| 编号 | 解法 | 机制 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| C1 | 滚动摘要(rolling summary) | 超预算的旧消息压成一段摘要,替换原文 | 简单、效果稳定 | 摘要会漂移(摘要的摘要) |
| C2 | 摘要 + 近期原文(Summary Buffer) | 摘要在前,最近 K 轮原文在后 | 兼顾记忆与新细节,工业界最常用 | 需要定 K 与预算 |
| C3 | 分层/递归摘要 | 分段摘要 → 再归并(map-reduce / refine) | 超长历史也能压 | 多次调用,延迟高 |
| C4 | 结构化事实抽取 | 不写自然语言,只抽 `{did, 结论, 已排除}` | 极小、可解释、可审计 | 需要定义字段与抽取规则 |
| C5 | 领域模板摘要 | 固定字段:用户意图 / 已查工具 / 关键结论 / 待办 | 输出稳定,易测试 | 只适合边界清晰的领域(钱包正好是) |
| C6 | 检索式记忆(替代摘要) | 旧对话入库,按需召回 | 上下文恒定,不丢细节 | 召回不准时"看起来失忆" |
| C7 | 分层记忆(MemGPT 式) | core / recall / archival 分级,模型自主换页 | 长任务强 | 工程重、调试难 |
| C8 | 摘要 + 校验回填 | 摘要后校验"关键实体是否还在",缺了补 | 降低失真 | 多一步校验 |

参考实现:LangChain 的 `ConversationSummaryBufferMemory`(C2)、`RefineDocumentsChain`/map-reduce(C3)、
[mem0](https://github.com/mem0ai/mem0)(C6)、[Letta/MemGPT](https://github.com/letta-ai/letta)(C7)。

## 4. 推荐设计(本项目)

### 4.1 先 C5 + C4,再考虑 C1/C2

钱包场景的对话**目的很窄**:查身份、查凭证、验凭证、看 DID 文档、问方法。
所以最划算的不是"通用摘要",而是**领域模板 + 结构化事实**:

```json
{
  "intent": "查某 DID 的凭证并逐张验证",
  "target": "did:swtc:jpAFbR1tzNMnmy4wfAycYtV33Jd288xYWx",
  "didTools": ["list_credentials", "verify_credential"],
  "findings": ["该 DID 名下 1 张 NFTOwnership", "凭证 #2 verified=true"],
  "open": ["其余 6 张未验证"],
  "dropped": 3
}
```

- `intent/target/findings/open` 进 `memory_facts`,随 system prompt 常驻(很小);
- `dropped` 记录被压缩掉的工具块数,便于复盘"模型为什么不知道某件事";
- 事实字段由**规则**从工具结果里提取(例如 `total`、`id`、`verified`),不依赖模型 —— 更稳、可单测。

### 4.2 预算与触发

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `CONTEXT_BUDGET_CHARS` | 24 000 | 近似 token:中文≈1 字符/token,英文≈4 字符/token |
| `SUMMARY_TRIGGER` | 预算的 80% | 到 80% 就压缩,留余量避免"压完又超" |
| `KEEP_RECENT_BLOCKS` | 6 | 最近 6 个工具块保留原文,其余压缩 |
| 摘要长度上限 | 400 字符 | 超了就是没压住 |

触发时机:**每轮 `plan_node` 组装消息之前**做一次判断(而不是每轮都摘要)。

### 4.3 若要用模型摘要(C1/C2)的提示词草案

```text
你是会话压缩器。把下面的历史压缩成不超过 5 行的事实清单,供后续回答使用。

必须保留:用户的目标、涉及到的 DID/凭证 id、已经得到的结论(含 verified 真假)、明确的排除项。
禁止:编造未出现的信息;保留寒暄与语气词;超过 5 行。
输出:每行一个 "- " 开头的事实,不要输出 JSON,不要解释你在做什么。

历史:
<history>
```

要点:**给出白名单与黑名单**(保留什么/禁止什么)、**限行数**、**要求纯文本**。
比"请总结一下"稳定得多。

### 4.4 失败降级(必须写进实现)

| 失败 | 降级 |
| --- | --- |
| 摘要调用超时 | 退回滑动窗口(S2):直接丢旧块 + 占位 |
| 摘要超长 | 截断到上限,并在 `dropped` 里记一笔 |
| 摘要里出现未出现的 id | 丢弃该行(可用正则/集合校验) |
| 摘要调用 4xx | 记日志,本轮用窗口,不重试(避免把失败放大) |

原则:**摘要是优化,不是正确性依赖**。摘要挂了,对话必须还能继续。

## 5. 怎么验证"摘要没把关键信息弄丢"

摘要质量没法靠单元测试证明,但可以做**回归样例**:

| 用例 | 输入 | 断言 |
| --- | --- | --- |
| 保留 DID | 用户给了 `did:swtc:j…`,随后 10 轮闲聊 | 摘要里必须出现该 DID |
| 保留结论 | 验证通过 `verified=true` | 摘要里必须出现"验证通过"或 `verified` |
| 不编造 | 历史里没有 NFT | 摘要不得出现 NFT |
| 长度 | 30 轮 | 摘要 ≤ 5 行且 ≤ 400 字符 |
| 降级 | 摘要器抛异常 | 本轮仍能回答(窗口兜底),且日志有 `summary_fallback` |

**顺序不能变**:先窗口(facts + trim),再摘要。窗口能解决 80% 的膨胀,摘要是在它之上"少丢一点",
直接做摘要会在没有预算判断的情况下反复压缩,成本和失真是双输。

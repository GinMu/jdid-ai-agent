# 检索:现在的 BM25、向量召回流程,以及索引选型

这份文档说明**现在用什么召回**、**向量召回的标准流程长什么样**、**索引怎么选**,
以及一个容易误解的问题:本项目**没有用 HNSW**,也没有向量索引。

> 结论先行:当前是**纯词法检索(BM25)**,语料只有 **113 块**。
> 这个规模下正确做法是"暴力打分"(flat),**HNSW 的收益为 0**、成本为正。
> 向量召回在本文里是"如果要引入"的完整方案,不是现状。

## 1. 现状:BM25,没有向量

| 项 | 现在 | 说明 |
| --- | --- | --- |
| 检索方式 | BM25(词法) | 英文按词、中文按二元组,`k1=1.5`、`b=0.75` |
| 索引结构 | **没有索引**,每次线性打分 | 113 块 × 几百 token,单次检索是微秒级 |
| 依赖 | 纯标准库(`math`/`re`/`collections`) | 不需要 embedding 模型、不需要向量库 |
| 语料 | `knowledge/did-methods.jsonl`(113 块) | 两个 DID 方法的注册表 + 规范 + 官网摘要 |

代码在 `src/did_ai_agent/knowledge.py`:`KnowledgeBase.search()` 对每块算分再排序。
之所以敢这么朴素:语料小、问题术语明确("did:swtc"、"ERC1056"、"注册表"这些词就是强信号)。

## 2. 向量召回是干什么的(作用)

BM25 的短板和向量的长处正好互补:

| 场景 | BM25 | 向量召回 |
| --- | --- | --- |
| 精确术语(`did:swtc`、`ERC1056`) | **强**:命中即高分 | 一般:数字/缩写容易被稀释 |
| 同义/改写("井证怎么注册" vs "Create") | 弱:词不匹配就零分 | **强**:语义相近即相近 |
| 跨语言(中文问、英文语料) | 很弱 | 强(多语言 embedding) |
| 可解释性 | 强:命中词可列出来 | 弱:相似度是个数 |
| 离线/依赖 | 无 | 要模型或 API |

所以"要不要向量"不是风格问题,而是:**用户会不会用与语料不同的词来问**。
钱包场景里"井证""身份""DID 文档"这些说法确实会漂,所以向量**有价值**,只是不该现在上。

## 3. 向量召回的标准流程

```text
离线(建库)                          在线(查询)
切块 → 归一化 → embedding → 索引      问题 → embedding → ANN top-N → 过滤/重排 → 拼上下文
       ↑ 一次性                        ↑ 每次请求
```

### 3.1 建库侧

| 步骤 | 做法 | 本项目对应 |
| --- | --- | --- |
| 切块 | 按标题/段落,≤800 字符 | 已有(`scripts/build_knowledge.py`) |
| 归一化 | 去多余空白、保留原始 `source` | 已有 |
| embedding | 每块一个向量,维度由模型决定 | 缺(需新增) |
| 写索引 | 向量 + id 落盘,建 ANN 索引 | 缺 |
| 版本化 | 语料变更 → 索引重建,模型变更 → **必须重建** | 缺 |

### 3.2 查询侧

| 步骤 | 做法 |
| --- | --- |
| 编码 | 用**同一个** embedding 模型把问题编码(模型不一致 = 向量空间错位) |
| 召回 | ANN 取 top-N(N 通常 20–50,比最终 k 大,留给重排) |
| 过滤 | 按 `kind`/`source` 白名单过滤(例如只查 spec) |
| 重排 | 可用更贵的模型或规则(术语命中加权) |
| 混合 | 与 BM25 结果融合,见 3.3 |
| 截断 | 取 k=4–8 拼进提示词,单片段上限 700 字符 |

### 3.3 混合检索(推荐形态)

单用向量会丢掉"精确术语"的优势,工业界默认是**混合**:

```text
score(d) = w1 * normalize(bm25(d)) + w2 * normalize(cosine(d))
# 或者更稳的 RRF(倒数排名融合):
rrf(d) = Σ 1 / (k + rank_i(d)),  k 取 60
```

RRF 的优点:不需要把两种分数归一化到同一量纲,对分数量纲不敏感;缺点:丢掉了分数间距信息。
本项目如果要做,建议**先 RRF**(实现 10 行),再考虑学习式融合。

## 4. 索引选型:为什么现在不该用 HNSW

| 索引 | 机制 | 适用规模 | 召回 | 内存 | 构建 | 增量 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **Flat(暴力)** | 逐个算相似度 | 10^2–10^4 | **精确** | 仅向量本身 | 无 | 天然支持 | **本项目应该用这个** |
| IVF / IVF-PQ | 聚类分桶 + 量化 | 10^5–10^7 | 高(可调 nprobe) | 小(PQ 可压缩 10×+) | 需训练 | 需重训 | 省内存,精度换空间 |
| **HNSW** | 多层邻近图,逐层贪心下降 | 10^4–10^8 | **很高** | 大(每向量额外边) | 较慢 | 支持插入 | 低延迟、少调参 |
| DiskANN | 图 + SSD | 10^8+ | 高 | 内存小(落盘) | 慢 | 有限 | 超大规模 |
| ScaNN / 其他 | 量化 + 分区 | 10^6+ | 高 | 中 | 中 | 有限 | 生态较少 |

### 4.1 HNSW 是什么

HNSW(Hierarchical Navigable Small World)把向量组织成**多层图**:上层稀疏用于"跳远",
下层稠密用于"精找"。查询从顶层入口点开始,逐层贪心走向距离更近的邻居,到底层得到近似最近邻。
三个关键参数:

| 参数 | 作用 | 常见取值 | 调大的代价 |
| --- | --- | --- | --- |
| `M` | 每个节点的邻居数 | 16–32 | 内存与构建时间上升,召回上升 |
| `efConstruction` | 建图时的候选队列长度 | 100–400 | 构建更慢,图质量更好 |
| `efSearch` | 查询时的候选队列长度 | 32–128 | 延迟上升,召回上升 |

### 4.2 HNSW 的优点(所以大家爱用)

| 优点 | 说明 |
| --- | --- |
| 查询快 | 近似对数复杂度,百万级仍能毫秒级 |
| 召回高 | 同参数下通常优于 IVF 系列 |
| 无需训练 | 与 IVF 不同,插入即建图 |
| 支持增量 | 新块可直接插入,不必全量重建 |
| 生态成熟 | `hnswlib`、`faiss`、`pgvector`、`Qdrant`、`Milvus` 都内置 |

### 4.3 HNSW 的代价(所以本项目不该用)

| 代价 | 说明 |
| --- | --- |
| 内存放大 | 除向量本身还要存图边;113 块纯属浪费 |
| 构建慢 | 大量插入时明显,而我们的语料是"一次性 113 块" |
| 删除弱 | 通常靠 tombstone,长期增删后要重建 |
| 需要调参 | `M`/`ef` 影响召回与延迟,不做评估等于碰运气 |
| **不解决我们的真实问题** | 113 块的暴力检索只要几十微秒,HNSW 省下的是 0 |

一句话:**HNSW 是"规模上来之后"的优化,不是"更高级的做法"**。在 10^2 量级用它,
等于给 113 行数据建一棵 B+ 树去找第 7 行。

## 5. 如果要上向量:推荐方案

| 决策 | 建议 | 理由 |
| --- | --- | --- |
| 什么时候上 | 语料 > 10^4 块,或评测显示 BM25 召回明显不足 | 否则只是增加依赖 |
| embedding 模型 | 本地 `bge-m3`(中英混排、多语言)或 API 向量模型 | 钱包资料中英混合;本地模型可离线 |
| 索引 | **先 Flat**,到 10^5 再换 HNSW | 规模决定结构,不要提前优化 |
| 存储 | 语料 JSONL + 向量 `.npz`/SQLite BLOB | 保持"随仓可运行"的轻量特性 |
| 融合 | RRF(k=60)混合 BM25 与向量 | 不依赖分数量纲 |
| 降级 | embedding 失败 → 回落 BM25 | 检索是增强,不是正确性依赖 |
| 评估 | recall@k、nDCG@10、P95 延迟 | 没有评估就不要调参 |

### 5.1 参数建议(真到 10^5 再抄)

```text
M = 16            # 内存与召回折中;>32 收益递减
efConstruction = 200
efSearch = 64     # 先按 P95 延迟定,再看召回
top-N(ANN) = 30   # 再重排/融合,最终只给模型 4–8 条
```

### 5.2 混合的实现骨架

```python
def hybrid_search(query: str, k: int = 4) -> list[Hit]:
    lexical = bm25.search(query, top_k=30)      # 已有
    dense = vector_index.search(embed(query), top_n=30)  # 新增
    return rrf([lexical, dense], k=k, rank_constant=60)
```

# 同一个模型,不同 Harness,成功率为什么差很多

这份文档解释一个常见困惑:模型没换、参数没换,换一套 Harness(脚手架)之后成功率差别巨大。
这是**工程事实**,不是玄学,也不是"模型时好时坏"。

> 结论先行:模型是**函数**,Harness 是**函数签名 + 数据管道 + 控制流 + 失败语义**。
> 成功率差异大多来自这四样,而不是模型的"聪明程度"。
> 换句话说:**Harness 决定了模型有没有机会做对,以及做错之后能不能自己发现。**

## 1. Harness 到底包含什么

| 组成 | 内容 | 对成功率的影响方式 |
| --- | --- | --- |
| 上下文 | system prompt、示例、注入资料、历史回放 | 模型看到什么,决定它能不能知道"该做什么" |
| 工具接口 | 工具名、描述、参数 schema、工具数量 | 选错工具、漏参数、乱编参数 |
| 观测格式 | 结果是 JSON 还是散文,字段叫什么,多大 | 读到却用不上,或把元信息当答案抄出来 |
| 控制流 | 单次 / ReAct / Plan-Execute,轮次上限,能否并行 | 步数不够做完、或绕圈子 |
| 失败语义 | 错误抛给用户,还是结构化回传给模型 | 决定"自纠率"——这是差异最大的一项 |
| 校验与修复 | 参数校验严格度、JSON 修复、重试 | 决定"错误是终点还是中间态" |
| 记忆与压缩 | 窗口、摘要、检索 | 长任务能不能保持目标一致 |
| 运行时 | 超时、限流、流式、工具延迟 | 超时被误判成"模型失败" |

同一个模型,只要其中一条不同,任务成功率就能差一截。研究界已经开始明确要求
"比较 agent 时要披露 harness":见 [Stop Comparing LLM Agents Without Disclosing the Harness](https://ar5iv.labs.arxiv.org/html/2605.23950)、
以及 SWE-agent 提出的"agent–computer interface 本身就是变量"
([论文](https://arxiv.org/abs/2405.15793v1)、[项目页](https://swe-agent.com/latest/background/))。
Anthropic 的 [Building effective agents](https://www.anthropic.com/research/harness-design-long-running-apps)
也把"该不该上 agent、用什么循环"作为首要设计问题。

## 2. 为什么差异是"乘法"而不是"加法"

多步任务的成败是逐步相乘的:设每步正确率 `p`,共 `L` 步,端到端成功率约 `p^L`。
(这是**示意**,真实任务里各步不独立,数字只为说明趋势。)

| 每步正确率 | 3 步 | 6 步 | 10 步 |
| --- | --- | --- | --- |
| 0.80 | 0.51 | 0.26 | 0.11 |
| 0.90 | 0.73 | 0.53 | 0.35 |
| 0.95 | 0.86 | 0.74 | 0.60 |

两点推论:

1. **Harness 的改进是复利**:把每步从 0.90 提到 0.95,6 步任务从 0.53 到 0.74;
2. **步数本身是成本项**:同样能力下,把 10 步压到 6 步(合并工具、预取),成功率自动上升。

## 3. 归因:怎么知道是哪一环

### 3.1 分解指标(别只看端到端)

| 指标 | 定义 | 差说明什么 |
| --- | --- | --- |
| 工具选择正确率 | 该调 A 调了 A | 工具名/描述/数量问题 |
| 参数正确率 | 必填参数齐、类型对 | schema 与描述问题 |
| 观测利用率 | 结果给了却没被引用 | 观测格式或体积问题 |
| 终止正确率 | 该停时停、不该停时不停 | 提示词与熔断问题 |
| 格式合规率 | 输出/调用可解析 | 协议与修复策略问题 |

### 3.2 消融(ablation)

固定模型与数据集,**一次只改一个 Harness 变量**,看指标变化。例:

```text
基线:提示词 A + 工具描述 B + JSON 观测 + ReAct + max_turns=6
变体1:只把工具描述写详细          → 看参数正确率
变体2:只把错误改成结构化回传       → 看自纠率/端到端
变体3:只把观测从 17KB 改成摘要     → 看观测利用率
```

### 3.3 轨迹审查

看**失败那一轮**的完整轨迹,而不是最终答案。在本项目里就是四条日志
(`chat` / `tool_request` / `resume` / `tool_result`,见 `docs/loop-guards.md`)。
最常见的三类真相:

- 工具根本没被调用(模型选错或没看懂描述);
- 调了但参数不对(描述没写清可选值);
- 结果给了但模型没用(观测太长/太杂,或和问题无关)。

### 3.4 统计别开玩笑

小样本对比没有意义:同一 harness 跑 20 次差 2 次可能就是噪声。建议
**每类任务 ≥100 次**,报告置信区间(Wilson 区间),并固定模型版本、提示词版本、Harness 版本。

## 4. 本项目的真实例子(都是踩过的)

| 现象 | 看起来像 | 实际是 | 修法 |
| --- | --- | --- | --- |
| 问"我有哪些凭证"永远 0 条 | 模型不会用工具 | 观测给的是**未解包的实体 JSON** | 先解实体再读,7 条才对 |
| 查别人 DID 却答成自己的 | 模型理解力差 | 工具**没有 `did` 参数** | 参数加 `did`,并在结果里回显 |
| 第二步工具必 400 | 模型不稳定 | thinking 模式要求回传 `reasoning_content`,库不回传 | 工具结果改文本回放 |
| 回答里全是 `\| a \| b \|` | 模型不会排版 | 客户端**没有 markdown 渲染** | 加轻量渲染器 |
| 开头冒出 "I'll look this up" | 模型话多 | 本地工具**无 `tool_request` 事件**,过渡语和答案粘在同一 draft | 提示词禁止过渡语 + 补分隔 |
| 长回答停在旧位置 | 模型输出不全 | 列表**不自动滚动** | 贴底跟随 |

共同点:**没有一条是"模型不行"**。把 harness 改对,同一个模型立刻"变聪明"。

## 5. 反模式

| 反模式 | 为什么有害 |
| --- | --- |
| 成功率低就换更大模型 | 掩盖 harness 缺陷,成本上升且问题仍在 |
| 提示词写成许愿("请尽量准确") | 没有可检验约束,等于没写 |
| 观测里塞原文/全量 JSON | 上下文被稀释,模型抓不住重点 |
| 错误只抛给用户 | 模型失去自纠机会,一步失败即整轮失败 |
| 无评估就调参 | 改动无法归因,越调越乱 |
| 用 20 个样本下结论 | 噪声当信号 |

## 8. 一句话总结

**模型决定"上限",Harness 决定"你离上限有多远"。**
当同一个模型在不同 Harness 里表现差异很大时,先怀疑上下文、工具接口、观测格式、失败语义,
再怀疑模型 —— 前四者才是我们真正能改的东西。

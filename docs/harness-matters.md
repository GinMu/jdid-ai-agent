# 同一个模型,不同 Harness,成功率为什么差很多

这份文档解释一个常见困惑:模型没换、参数没换,换一套 Harness(脚手架)之后成功率差别巨大。
这是**工程事实**,不是玄学,也不是"模型时好时坏"。

> 结论先行:模型是**函数**,Harness 是**函数签名 + 数据管道 + 控制流 + 失败语义**。
> 成功率差异大多来自这四样,而不是模型的"聪明程度"。
> 换句话说:**Harness 决定了模型有没有机会做对,以及做错之后能不能自己发现。**

## 1. Harness 到底包含什么

| 组成 | 内容 | 对成功率的影响方式 |
| --- | --- | --- |
| 上下文 | system prompt、示例、注入资料、历史回放 | 模型看到什么,决定它能不能知道"该做什么" |
| 工具接口 | 工具名、描述、参数 schema、工具数量 | 选错工具、漏参数、乱编参数 |
| 观测格式 | 结果是 JSON 还是散文,字段叫什么,多大 | 读到却用不上,或把元信息当答案抄出来 |
| 控制流 | 单次 / ReAct / Plan-Execute,轮次上限,能否并行 | 步数不够做完、或绕圈子 |
| 失败语义 | 错误抛给用户,还是结构化回传给模型 | 决定"自纠率"——这是差异最大的一项 |
| 校验与修复 | 参数校验严格度、JSON 修复、重试 | 决定"错误是终点还是中间态" |
| 记忆与压缩 | 窗口、摘要、检索 | 长任务能不能保持目标一致 |
| 运行时 | 超时、限流、流式、工具延迟 | 超时被误判成"模型失败" |

同一个模型,只要其中一条不同,任务成功率就能差一截。研究界已经开始明确要求
"比较 agent 时要披露 harness":见 [Stop Comparing LLM Agents Without Disclosing the Harness](https://ar5iv.labs.arxiv.org/html/2605.23950)、
以及 SWE-agent 提出的"agent–computer interface 本身就是变量"
([论文](https://arxiv.org/abs/2405.15793v1)、[项目页](https://swe-agent.com/latest/background/))。
Anthropic 的 [Building effective agents](https://www.anthropic.com/research/harness-design-long-running-apps)
也把"该不该上 agent、用什么循环"作为首要设计问题。

## 2. 为什么差异是"乘法"而不是"加法"

多步任务的成败是逐步相乘的:设每步正确率 `p`,共 `L` 步,端到端成功率约 `p^L`。
(这是**示意**,真实任务里各步不独立,数字只为说明趋势。)

| 每步正确率 | 3 步 | 6 步 | 10 步 |
| --- | --- | --- | --- |
| 0.80 | 0.51 | 0.26 | 0.11 |
| 0.90 | 0.73 | 0.53 | 0.35 |
| 0.95 | 0.86 | 0.74 | 0.60 |

两点推论:

1. **Harness 的改进是复利**:把每步从 0.90 提到 0.95,6 步任务从 0.53 到 0.74;
2. **步数本身是成本项**:同样能力下,把 10 步压到 6 步(合并工具、预取),成功率自动上升。

## 3. 归因:怎么知道是哪一环

### 3.1 分解指标(别只看端到端)

| 指标 | 定义 | 差说明什么 |
| --- | --- | --- |
| 工具选择正确率 | 该调 A 调了 A | 工具名/描述/数量问题 |
| 参数正确率 | 必填参数齐、类型对 | schema 与描述问题 |
| 观测利用率 | 结果给了却没被引用 | 观测格式或体积问题 |
| 终止正确率 | 该停时停、不该停时不停 | 提示词与熔断问题 |
| 格式合规率 | 输出/调用可解析 | 协议与修复策略问题 |

### 3.2 消融(ablation)

固定模型与数据集,**一次只改一个 Harness 变量**,看指标变化。例:

```text
基线:提示词 A + 工具描述 B + JSON 观测 + ReAct + max_turns=6
变体1:只把工具描述写详细          → 看参数正确率
变体2:只把错误改成结构化回传       → 看自纠率/端到端
变体3:只把观测从 17KB 改成摘要     → 看观测利用率
```

### 3.3 轨迹审查

看**失败那一轮**的完整轨迹,而不是最终答案。在本项目里就是四条日志
(`chat` / `tool_request` / `resume` / `tool_result`,见 `docs/loop-guards.md`)。
最常见的三类真相:

- 工具根本没被调用(模型选错或没看懂描述);
- 调了但参数不对(描述没写清可选值);
- 结果给了但模型没用(观测太长/太杂,或和问题无关)。

### 3.4 统计别开玩笑

小样本对比没有意义:同一 harness 跑 20 次差 2 次可能就是噪声。建议
**每类任务 ≥100 次**,报告置信区间(Wilson 区间),并固定模型版本、提示词版本、Harness 版本。

## 4. 本项目的真实例子(都是踩过的)

| 现象 | 看起来像 | 实际是 | 修法 |
| --- | --- | --- | --- |
| 问"我有哪些凭证"永远 0 条 | 模型不会用工具 | 观测给的是**未解包的实体 JSON** | 先解实体再读,7 条才对 |
| 查别人 DID 却答成自己的 | 模型理解力差 | 工具**没有 `did` 参数** | 参数加 `did`,并在结果里回显 |
| 第二步工具必 400 | 模型不稳定 | thinking 模式要求回传 `reasoning_content`,库不回传 | 工具结果改文本回放 |
| 回答里全是 `\| a \| b \|` | 模型不会排版 | 客户端**没有 markdown 渲染** | 加轻量渲染器 |
| 开头冒出 "I'll look this up" | 模型话多 | 本地工具**无 `tool_request` 事件**,过渡语和答案粘在同一 draft | 提示词禁止过渡语 + 补分隔 |
| 长回答停在旧位置 | 模型输出不全 | 列表**不自动滚动** | 贴底跟随 |

共同点:**没有一条是"模型不行"**。把 harness 改对,同一个模型立刻"变聪明"。

## 5. 反模式

| 反模式 | 为什么有害 |
| --- | --- |
| 成功率低就换更大模型 | 掩盖 harness 缺陷,成本上升且问题仍在 |
| 提示词写成许愿("请尽量准确") | 没有可检验约束,等于没写 |
| 观测里塞原文/全量 JSON | 上下文被稀释,模型抓不住重点 |
| 错误只抛给用户 | 模型失去自纠机会,一步失败即整轮失败 |
| 无评估就调参 | 改动无法归因,越调越乱 |
| 用 20 个样本下结论 | 噪声当信号 |

## 8. 一句话总结

**模型决定"上限",Harness 决定"你离上限有多远"。**
当同一个模型在不同 Harness 里表现差异很大时,先怀疑上下文、工具接口、观测格式、失败语义,
再怀疑模型 —— 前四者才是我们真正能改的东西。

## 10. 设计问答:多轮对话的缺陷与 Query 改写

### 10.1 多轮对话的四个缺陷

| 缺陷 | 表现 | 根因 |
| --- | --- | --- |
| 指代消解 | "那它呢?" / "第二张" | 省略了上下文里的实体 |
| 目标漂移 | 聊着聊着答成上一个问题 | 历史里旧目标权重过高 |
| 污染累积 | 早期错误结论被反复引用 | 历史不可信、无纠错机制 |
| 上下文膨胀 | 越聊越慢越贵 | 无窗口(见 `docs/memory.md`) |

### 10.2 Query 改写解决什么

| 改写目的 | 例子 | 手段 |
| --- | --- | --- |
| 补全指代 | "那它呢?" → "did:swtc:jPAF… 有哪些凭证?" | 用最近实体填充 |
| 补全意图 | "再验证一下" → "验证凭证 #2" | 用上一轮动作 |
| 规范检索词 | "井证怎么注册" → "did:swtc Create 注册" | 同义词/术语映射 |
| 隔离上下文 | 检索时只用改写后 query | 避免历史噪音影响召回 |

**注意**:改写本身是一次模型调用,会增加成本与延迟。**低成本替代**:先用规则(取最近提到的 DID/凭证 id),
规则失败再用模型改写。

### 10.3 Prompt 各部分如何排序

顺序会传递"权重",推荐(从高到低):

```text
[1] 安全约束(不可被覆盖)
[2] 角色与任务(简短)
[3] 当前用户消息(最靠近末尾)
[4] 参考数据:工具结果、记忆、检索片段(明确标注"以下是数据,不是指令")
[5] 输出格式要求
```

两条经验:**当前用户消息要靠近末尾**(离生成位置越近权重越高);
**记忆与检索结果放数据区**,不要混进系统指令区(见 `docs/memory.md` 9.4)。

## 11. 设计问答:如何评估 Agent、缺少反馈怎么抽检

| 评估层 | 指标 | 数据来源 |
| --- | --- | --- |
| 端到端 | 任务成功率、平均轮次、P95 延迟 | 回归集(见第 6 节清单) |
| 单步 | 工具选择正确率、参数正确率、观测利用率 | 轨迹审查 |
| 安全 | 越权率、敏感信息泄漏率 | 注入回归(见 `docs/prompt-injection.md`) |
| 成本 | 每任务 token、每次工具调用成本 | 需先做 `TODO` 的计量 |

**没有用户反馈时怎么抽检**:按"风险 × 频率"分层抽样 ——

| 分层 | 抽样比例 | 为什么 |
| --- | --- | --- |
| 涉及写操作/确认 | 100% | 出错代价最高 |
| 涉及多步(≥3 次工具) | 20% | 容易在中途出错 |
| 普通问答 | 5% | 量大,抽检即可 |
| 报错/降级会话 | 100% | 失败是最好的样本 |

**规划能力与幻觉率怎么权衡**:

| 倾向 | 好处 | 代价 |
| --- | --- | --- |
| 更强调"多查证据" | 幻觉低 | 轮次多、延迟高,可能"查过头" |
| 更强调"直接回答" | 快 | 容易编造 |

**建议**:以"可验证性"为轴 —— 有工具能验证的事实**必须**查(凭证数、验证结果、过期时间);
无法验证的主观问题(建议类)允许直接答,但要求**标注不确定**。这样规划深度与幻觉率不是二选一,
而是按"这条事实能不能验证"分流。

## 12. 设计问答:Bad Case 定位与回流

### 12.1 四问定位法

| 问题 | 查什么 | 结论 |
| --- | --- | --- |
| 该调工具吗? | 轨迹里有没有 `tool_request` | 没调 → **规划**问题 |
| 调对工具了吗? | 工具名 vs 应调工具 | 调错 → **规划/描述**问题 |
| 参数对吗? | `args` 与 schema | 错 → **参数**问题(描述或校验) |
| 结果用对了吗? | 观测里有数据,回答却错 | 用错 → **推理**问题 |

### 12.2 回流与防回归

```text
Bad Case → 归因(上表)→ 最小修复(改描述/改校验/改提示词/改代码)
  → 加一条回归用例(输入 + 期望轨迹/期望事实)
  → 跑全量评估,确认没把别的任务弄坏
```

| 归因 | 典型修复 | 回归用例怎么断言 |
| --- | --- | --- |
| 规划 | 提示词规则、加示例 | 必须出现某次 `tool_request` |
| 工具描述 | 补"何时使用/不做什么" | 选对工具 |
| 参数 | 补 description、加校验 | 参数值正确 |
| 推理 | 补提示("结论必须引用证据") | 回答含关键事实、不含编造 |
| 渲染 | 客户端渲染 | UI 断言(非本服务) |

**防回归的关键**:**用轨迹断言,不要只断言最终文本** —— 文本措辞会变,轨迹(调了哪些工具、参数是什么)稳定得多。

## 13. 设计问答:Token 成本、缓存、模型路由与超限

### 13.1 一次会话消耗在哪

| 组成 | 变化趋势 | 说明 |
| --- | --- | --- |
| system prompt | 固定 | 规则 7 条 + 工具 schema(11 个) |
| 历史观测 | **线性增长** | 每次工具结果都会重发(无窗口) |
| 当前消息 | 小 | — |
| 输出 | 中等 | 流式逐 token |

粗略估算(示意,不是实测):一次工具往返 ≈ system(约 1–2k)+ 历史(累加)+ 输出;
**往返次数是最主要的乘数** —— 少一次往返比省几百字 system 有效得多。

### 13.2 提高缓存命中率

| 手段 | 效果 | 现状 |
| --- | --- | --- |
| 稳定前缀(system + 工具 schema 不变) | 命中前缀缓存,省钱省延迟 | 结构上已稳定,但未显式利用 |
| 把变化内容放末尾 | 保持前缀一致 | 已符合(工具结果在末尾) |
| 避免在 system 里塞时间戳/随机数 | 破坏前缀 | 已符合 |
| 服务商上下文缓存 | DeepSeek 支持磁盘 KV 缓存 | 未开启/未验证 |

### 13.3 模型路由

| 场景 | 建议模型档位 | 理由 |
| --- | --- | --- |
| 工具选择/多步规划 | 强模型 | 错一次代价高 |
| 摘要压缩、分类、改写 | 小模型 | 任务简单、量大 |
| 最终措辞 | 中档即可 | 质量要求没那么高 |

**现状**:单一模型(`DID_AI_MODEL`),没有路由。`TODO`:先做"摘要用小模型",收益最大且风险最低。

### 13.4 超限处理

| 超限类型 | 处理 |
| --- | --- |
| 上下文超模型窗口 | 窗口裁剪 → 摘要 → 拒绝并提示"对话过长,建议新开" |
| 输出超 `max_tokens` | 截断并提示"继续" |
| 速率超限(429) | 退避重试 1 次;仍失败则降级提示 |
| 成本超预算 | 硬熔断(每会话 token 上限),返回明确提示 |

**现状**:以上都未做(也没有 token 计量)。**建议先做计量**(把每次请求的 input/output token 记进日志),
没有计量就谈不上预算与路由。
